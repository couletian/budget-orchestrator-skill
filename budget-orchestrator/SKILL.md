# 预算编排器（Budget Orchestrator）

## 它解决什么

用户给出一个预算（token 数，或某个模型官方计价下的金额），要求任务**在该预算内尽量完成得最好**。
本 skill 提供三件东西：

1. **确定性账本**：旁路读取 `~/.workbuddy/projects/**/*.jsonl` 里每条请求的**真实 usage**，
   实时累计 token 与金额。口径与 `token-dashboard` skill 完全一致（已交叉验证逐项相等）。
2. **实时可视化面板**：任务树与子任务进度、token/金额消耗、速率与预计触顶时间、事件日志，
   以及暂停/追加预算/切换模式的操作入口。
3. **控制面**：CLI + HTTP + MCP 三种接法，把预算状态和"喊停"信号交给 agent 与用户。

> **关于"包含工具自身的耗费"**：账本统计的是**整个会话（含所有子代理、含监督与评审 agent）**
> 的真实消耗，因此协调开销、监督开销天然被计入同一预算，不需要额外估算。
> `reserve_pct`(默认 15%) 只是额外建议留出的安全余量。

## 快速开始

用**本机托管 Python 运行时**调用（绝对路径，见 `<binary_context>`；任选一个 3.8+ 解释器即可，无第三方依赖）：

```bash
# 1) 启动（后台）：设定预算并开始监听 + 起面板
<python> <skill>/bo.py daemon start --tokens 3000000 --cny 20

# 2) 看状态
<python> <skill>/bo.py status

# 3) 打开面板
<python> <skill>/bo.py url            # 会打印 http://127.0.0.1:<port>/
```

### 🩺 面板打不开？先看这一条（沙箱 / CI 环境必读）

**症状**：`daemon start` 打印"已启动"并且当场探测端口是通的，但用户打开
`http://127.0.0.1:<port>/` 却显示**无法连接**；`daemon status` 随后报"未运行"。

**原因**：`daemon start` 用 `DETACHED_PROCESS` 拉起面板进程。在**命令沙箱、CI、
部分 IDE 终端**里，宿主会在**每次命令调用结束**时回收该次调用派生的所有子进程 ——
脱离进程也不例外。于是命令自己校验时端口通，shell 一返回进程就被杀。
（诊断特征：`netstat` 只剩几条指向该端口的 `TIME_WAIT`，那是命令自己探测留下的。）

**修复**：改用**看守进程**，并把它交给宿主的**长驻后台任务**托管：

```bash
<python> <skill>/bo.py respawn --port 8801 --cny 0.2 --interval 3
# 用宿主的长驻后台任务机制运行上面这条（而不是普通 & 后台），
# 看守进程会持续守护：端口掉线即自动重拉面板，新 pid 写入 daemon.pid
```

自检（应当先掉线、几秒后恢复，HTTP 200）：

```bash
# 杀掉当前监听者，等待一个 interval，再查
netstat -ano | grep 127.0.0.1:<port> | grep LISTEN
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:<port>/
```

> 判断口诀：**"当场通、随后断"→ 一定是子进程被回收，用 `respawn` + 长驻托管。**
> 普通本机终端无此限制，`daemon start` 直接可用。

### 手动关闭面板（面板内「关闭面板」按钮）

面板右下角有 **关闭面板** 按钮，用于**主动彻底关闭**面板进程，而不是只关浏览器标签页。
它做两件事：写标记文件 `<data-dir>/panel.disabled`，然后退出面板进程。

看守进程**会尊重这个标记**（检测到就停手，不再无脑重拉）—— 这正是它与"进程被杀"的区别：
- **进程意外死亡** → 看守进程重拉（保证可用性）
- **用户主动关闭** → 看守进程停手（尊重意志）

**重新唤起**（标记会被自动清除，一次性可恢复）：

```bash
<python> <skill>/bo.py daemon start --port 8801 --cny 0.2   # 或
<python> <skill>/bo.py respawn --port 8801 --cny 0.2
```

`daemon status` 在手动关闭后会明确提示：
`daemon 未运行（面板已被手动关闭；用 daemon start 或 respawn 可重新唤起）`。

> 关闭面板**不影响账本与预算**：数据仍在 `<data-dir>/ledger.db`，只是不再有服务进程推送。
> 想立刻恢复：`daemon start` 时会自动清标记并起服务。

### ♻️ 每次重新用本技能：`respawn` 一定重新建得起来

**你可能在 WorkBuddy 里手动取消托管看守进程的后台任务。** 这是允许的 ——
下次使用本技能时，**直接再跑一次 `respawn` 即可**，不需要先清理任何旧状态。它是**幂等**的：

1. **无条件清除残留的「手动关闭」标记** —— 不会因为上次残留而拒绝启动；
2. **自动避开被占用的端口**（顺序向后找可用端口）；
3. **若面板已在运行则接管守护**，不重复起实例（例如上次任务其实没被取消）。

```bash
# 每次开工，这一条就够了（换端口只会发生在原端口被外人占用时）
<python> <skill>/bo.py respawn --port 8801 --cny 0.2
```

> 口诀：**`respawn` 可以且应当被反复调用。** 它既负责"重新创立看守进程"，
> 也负责清理上次留下的状态 —— 把"手动关了后台任务怎么办"这件事收敛成一条幂等命令。

### ⚠️ 启动后第一件事：把看板交给用户（必做，不可省略）
`daemon start` / `run` 会打印面板地址。**启动成功后必须立即**执行以下二者之一：

1. **推荐** —— 用 `present_files` 把 `http://127.0.0.1:<port>/` 打开给用户。
   面板是 SSE **实时刷新**的，用户能直接看到预算进度、任务树、消耗曲线、自主协调指令；
2. **退一步** —— 在回复的**第一行**明确写出面板端口与完整地址。

这条不是可选项：预算约束的价值有一半来自可见性 ——
用户看不见消耗，就无法及时喊停、改预算、调优先级。

也可以让工具自己尝试拉起系统浏览器（本机运行有效）：

```bash
<python> <skill>/bo.py daemon start --tokens 3000000 --cny 20 --open
```

**默认只统计"启动之后"的消耗**（符合"任务预算"语义）。要统计历史全量用 `--since all`；
要统计近 N 秒用 `--since 600`。

工作区默认取当前目录对应的 slug；也可用 `--workspace <slug>` 指定，或 `--all` 汇总所有工作区。

## Agent 协作协议（重要）

预算能否守住，取决于各角色是否遵守同一套纪律。默认角色分工：

| 角色 | 由谁承担 | 职责与动作 |
|---|---|---|
| **Orchestrator** | 主 agent | 接收用户预算 → `daemon start` → 分析并拆解、规划任务（不能只等预算不够了才开始思考如何缩减任务，而是从一开始就做足够科学合理地分析来规划如何在预算范围内高质量完成任务） → 分配子任务预算 → 汇总交付 |
| **Planner** | 主 agent / 子代理 | 用 `task --cny M --priority N add <id> --name "..."` 声明子任务、**额度**与优先级（两者都要给） |
| **Executor** | 主 agent / 子代理 | 执行前 `task use <id>`，让消耗归入该子任务 |
| **Supervisor** | **autopilot 引擎**（确定性）+ agent 执行 | 定期产出调整指令，agent 照做 |
| **Reviewer** | 子代理 | 评估完成度；预算紧张时按指令收敛范围 |

**核心原则：AI 自行协调为主，人工只保留否决权。不能只等预算不够了才开始思考如何缩减任务，而是从一开始就做足够科学合理地分析来规划如何在预算范围内高质量完成任务。**

工作循环只有三步，**不要中途停下来请示**：

```
起监视器 → **把看板交给用户** → 拆解子任务并标好主干
   ↓
【规划达成】向用户确认优先级（只问一次）→ `bo.py plan` 校验
   ↓                                    └─ 不通过就回到上一步调整
[执行] ←───────────────────┐
   ↓                       │
每完成一个子任务 / 每 2-3 次工具调用
   ↓                       │
调用 boc_autopilot 取指令 ──┘ 自行执行动作后**继续推进**
```

```bash
<python> <skill>/bo.py autopilot     # 退出码 0=proceed 3=adapt 4=escalate
```

| 返回 | AI 该做什么 |
|---|---|
| `proceed` | 预算充裕，按照最初计划正常推进，无需调整 |
| `adapt` | **执行指令里的 actions，然后继续推进** —— 不是停下来请示 |
| `escalate` | 降级阶梯已用尽，此时才向用户说明并请求追加 |

`adapt` 给出的是**结构化可执行动作**（每条标明对应 YAGNI 阶梯第几级），例如：
爬 YAGNI 阶梯、压缩上下文、换更省的模型、减少评审轮次、跳过非关键子任务、只保主干。
**执行完直接继续；不要输出"是否继续"之类的询问。**

**子任务优先级与额度**（`--priority 1..5`，≥4 视为主干）：

```bash
# ✅ 推荐写法：额度/优先级旗标写在动作词（add）之前
<python> <skill>/bo.py task --cny 0.045 --priority 5 add T1 --name "核心功能"   # 主干，任何情况都保住
<python> <skill>/bo.py task --cny 0.030 --priority 2 add T2 --name "锦上添花"   # 非主干，告急时会被建议跳过
```

> ⚠️ **不要漏掉 `--cny` / `--tokens`。**
> 不写额度的子任务会进 `plan` 的 `unbudgeted` 清单，判定直接变 `tight`，
> 并附上「未标额度就无法参与取舍计算」——**预算不够时工具不知道该砍谁**。
> 实测踩过这个坑：示例里只写了 `--name`/`--priority`，照抄就得到一堆无额度任务。

> ⚠️ **旗标不要重复。** argparse 是「后者静默覆盖前者」：
> `task --cny 0.045 add T1 --cny 0.02` 最终只记 0.02，前一个值无声消失。
> 工具现在会打印 `[warn] --cny 出现 2 次…`，但别依赖它兜底。

> ℹ️ 当前版本两种位置其实都能解析（argparse 允许选项与位置参数交错），
> 但**统一前置**是有意为之：语义无歧义，且将来若把 `task add` 改成真正的子子命令，
> 写在后面的旗标会变成静默失效。前置写法对两种结构都安全。

优先级是 AI 自主取舍的**唯一依据** —— 不标优先级，工具就无法判断该砍谁。

> 事后补记或改优先级：`task --cny 0.045 add T3 --name "..."`、
> `task prio T2 --priority 1`。

**人工干预（始终可用，但不是主路径）**：

| 动作 | 命令 |
|---|---|
| 暂停 / 恢复 / 终止 | `control pause\|resume\|stop` |
| 追加预算（自动解除暂停） | `budget --add-cny N` |
| 调整任务重要性 | `task prio T2 --priority 1` |
| 切成"超预算就硬停等人"的保守模式 | `mode enforce` |

**预算分配建议**：主干子任务合计不要超过可用额度的 70%，留出重试与收敛余量。

## 规划达成（开工前必做）

拆完子任务、**还没动手**时，先走完这两步。协议要求"从一开始就做足够科学合理地分析
来规划如何在预算范围内高质量完成任务"—— 本节就是它的落地动作。

### 第一步：向用户确认优先级（只问一次）

用 `AskUserQuestion` 把拆解结果摆给用户，让他确认或调整**哪个是主干**。
AI 先给出**建议优先级**，用户只需确认或改动 —— 不要开放式地问"你想怎么做"。

确认后用 `task prio <id> --priority N` 落到任务树上。

> 这不是"逐次请示"。执行过程中仍由 AI 自主推进；
> 只在**规划阶段**确认一次取舍口径 —— 之后的降级才有依据。

### 第二步：规划校验

```bash
<python> <skill>/bo.py plan      # 退出码 0=合理 3=偏紧 4=超额
```

它回答三件事：

1. 子任务额度合计是否超出总额度；
2. 主干额度占比是否 ≤ 70%（建议线）；
3. **预算不够时该牺牲谁** —— 按 `(优先级升序, 额度降序)` 排出牺牲顺序与砍多少。

| 结论 | 该做什么 |
|---|---|
| `ok` | 按计划开工 |
| `tight` | 先补齐**未标额度**的任务，或降低主干占比，再开工 |
| `over` | **先按给出的顺序牺牲，或带着这份预案问用户** —— 不要先做再说 |

**这一步的意义**：让 `autopilot` 后续的 `adapt` 变成**兑现预案**，
而不是现场拍脑袋决定砍谁。

## 瘦身纪律（融合 ponytail）

预算有两侧：**需求侧**是计量与喊停（上面的账本与阈值），**供给侧**是"同样的任务用更少的消耗做完"。
下面这套把 ponytail 的 YAGNI 阶梯与输出纪律，从"行为习惯"变成**可测量、可自动触发**的机制。

**系统会按预算消耗自动升级瘦身强度**（`status` / `check` / 面板都会显示当前档位）：

| 预算已用 | 档位 | 纪律 |
|---|---|---|
| < 60% | `normal` 常规 | 保持预算意识，按照最初计划正常推进 |
| 60–80% | `lite` 轻瘦身 | 继续做，但每步附一句更省的做法供选择 |
| 80–95% | `full` 强制阶梯 | 执行 YAGNI 阶梯；代码优先、解释≤3 行；非关键子任务换小模型或砍掉 |
| ≥ 95% | `ultra` 极端瘦身 | 只交主干，其余当场砍掉并说明；先给最省的一行方案，再质疑需求本身 |

**YAGNI 阶梯（停在第一个成立的级别）**

1. 这一步是否真的需要存在？—— 推测性需求直接跳过，一句话说明理由
2. 本仓库 / 本会话里已经有现成的？—— **先找再写**，重复实现是最常见的浪费
3. 标准库能做？—— 用标准库，不写等价的自研实现
4. 平台原生能力覆盖？—— 用原生特性替代第三方依赖
5. 已安装的依赖能解决？—— 不为几行代码新增依赖
6. 能一行搞定？—— 一行
7. 才写最少可运行代码 —— 最短可行 diff 即完成

**输出纪律**：代码优先，解释不超过三行。解释比代码长就删解释。
不写单实现抽象、不为将来留脚手架、删优于加。

**无论多紧都不能省**：信任边界的输入校验、防止数据丢失的错误处理、安全措施、
用户明确要求的内容、**一处可运行的检查**（非平凡逻辑必须留一个最小可跑验证）。

**看哪里在漏**

```bash
<python> <skill>/bo.py lean        # 加 --json 取结构化结果
```

它指出四类可压缩项并标明对应阶梯级别：**返工**（同一目标被反复改 / 整体重写）、
**上下文膨胀**（单次输入过大）、**输出冗长**、**工具热点**。

> **诚实边界**：`lean` 只报**可数的实测事实**（重复次数、关联消耗、异常大请求），
> **绝不虚构"你省了 N token"** —— 没写出来的版本不存在，没有基线可减。
> 这条已写成单元测试 `test_never_fabricates_savings`，防止日后被"优化"掉。

## 命令参考

| 命令 | 作用 |
|---|---|
| `bo.py daemon start\|stop\|status` | 后台运行（监听 + 面板） |
| `bo.py respawn` | **看守进程**：面板掉线自动重拉（沙箱/CI 必用，交长驻后台任务托管） |
| `bo.py run --force` | 忽略「面板已手动关闭」标记，强制启动面板 |
| `bo.py run` | 前台运行（调试用，Ctrl+C 退出） |
| `bo.py status [--json]` | 预算/用量/速率/模型/任务树/降级建议 |
| `bo.py check [--json]` | 轻量判定 GO / DEGRADE / STOP（退出码 0/3/4） |
| `bo.py budget --tokens N --cny M [--soft 70 --hard 100]` | 设置预算与阈值 |
| `bo.py budget --add-tokens N --add-cny M` | 追加额度（自动解除暂停） |
| `bo.py control pause\|resume\|stop [--reason ...]` | 中断控制 |
| `bo.py mode auto\|observe\|enforce` | 自主协调（默认）/ 只观测 / 超预算即硬停等人 |
| `bo.py task add\|use\|done\|list\|rm\|rm-all` | 任务树与分项预算 |
| `bo.py task --cny M --priority N add <id> --name "..."` | **正确姿势**：额度/优先级旗标写在动作词**之前** |
| `bo.py reset [--keep-budget]` | 账本归零：停 daemon + 备份 `ledger.db` 三件套后重新起算 |
| `bo.py run --since now` | 只把**统计起点**推到此刻（不清历史，最轻的归零方式） |
| `bo.py lean [--json]` | 精简审计：YAGNI 阶梯 + 输出纪律，指出可压缩项 |
| `bo.py autopilot [--json]` | **自主协调指令**：0=继续 3=降级后继续 4=才需人工 |
| `bo.py plan [--json]` | **规划校验**：额度是否装得下子任务 + 取舍预案（0=合理 3=偏紧 4=超额） |
| `bo.py task prio <id> --priority N` | 调整子任务重要性（影响 AI 取舍） |
| `bo.py report --out file.json` | 导出全量报告（审计用） |
| `bo.py url` | 打印面板地址 |

通用参数：`--data-dir`（数据目录）、`--projects`（日志目录）、`--workspace`、`--all`。

## 账本会被历史撑爆？先分清两种情况

面板显示「已用 4090%」这类离谱数字，只有两种成因，处理方式完全不同：

**情况一：旧任务的历史请求还在被统计（已修复）**

账本的 `totals()` 过去**不带时间过滤**，而 `plan`/`lean`/按模型分布全都按
统计起点（`meta.since_ts`）过滤 —— 口径不一致，于是上一轮任务的消耗继续累加进
「已用」，金额百分比直接冲上几千。现在 `totals()` 也按 `since_ts` 统计，
预算与"已用"重新同一口径。

如果用的是旧版本账本、或确实想把起算点推到此刻：

```bash
<python> <skill>/bo.py run --since now      # 推荐：只推起点，历史仍可查
```

**情况二：真的要一本全新的账（归零 + 备份）**

```bash
<python> <skill>/bo.py daemon stop          # 必须先停，守护进程在写时改名会 PermissionError
<python> <skill>/bo.py reset                # 自动停 daemon + 备份三件套 + 重新起算
<python> <skill>/bo.py reset --keep-budget  # 只清历史用量，保留预算设置与任务树
```

若坚持手工做，**必须把 `ledger.db` 连同 `-shm` / `-wal` 一起备份改名**：

```bash
cd ~/.workbuddy/budget-orchestrator
S=$(date +%Y%m%d-%H%M%S); mkdir -p backup
[ -f ledger.db     ] && mv ledger.db     "backup/ledger-$S.db"
[ -f ledger.db-shm ] && mv ledger.db-shm "backup/ledger-$S.db-shm"
[ -f ledger.db-wal ] && mv ledger.db-wal "backup/ledger-$S.db-wal"
```

（`bo.py reset` 产出的备份就是这个命名：`backup/ledger-<时间戳>.db[-shm|-wal]`。）

> **为什么不能只搬 `ledger.db`**：SQLite 处于 WAL 模式。**回滚时**更危险 ——
> 若只把主库放回、却留下新账本产生的 `-wal`，SQLite 会把那个 WAL 当成
> 自己的日志**重放**，于是空账本的页覆盖掉刚放回去的旧数据，历史直接消失。
> 这条已在单元测试里固定住（`test_reset_preserves_rollback_data`）。
> **三件套同进同出**，改名之后才谈得上"从零起算"。
> `bo.py reset` 已内建这条纪律：改名失败会报错中止（不静默半搬），
> 收工时会主动关闭连接释放句柄。

> **为什么必须先停 daemon 与看守进程**：守护进程持有账本句柄，Windows 下改名会
> `PermissionError`（`WinError 32`）。`reset` 会先替你 `taskkill` —— 而且会
> **先停看守进程（respawn）再停面板**：看守进程既持句柄、又会立刻把面板重新拉起来，
> 只停面板等于白停（实测：`reset` 直接报 `WinError 32` 中止）。
> 看守进程的 pid 记在 `<data-dir>/watch.pid`。

## 面板

`http://127.0.0.1:<port>/`，深/浅色可切，SSE 每秒推送。展示：
预算进度条（带软/硬阈值刻度）、KPI（已用 token/金额/剩余/速率/预计触顶/输入输出比/**监听**）、
任务树（含子任务进度条）、按模型与按执行体分布、近 60 分钟用量时间线、事件日志；
并提供**暂停 / 恢复 / 停止 / 追加预算 / 切换模式 / 导出 JSON** 的操作入口。

**「监听」这张卡是回答"看板是不是卡住了"的**：

| 显示 | 含义 | 该怎么办 |
|---|---|---|
| `已读到底` | 采集已把日志读到最后一行 | 面板没变化是**宿主还没把新行落盘**（日志按消息粒度追加，不是连续流），等下一次落盘即可 |
| `待读 N B` | 还有 N 字节新日志没读 | 正常，下一个轮询周期（默认 1–1.5 s）就消化掉 |

命令行同样可见：`bo.py status` 末尾会打印
`监听  N 个日志文件  已读到日志末尾 / 尚有 X 字节待读` 与 `日志最后写入 <时间>`。

> **实时性的真实上限**：采集侧是每秒轮询 + 游标增量读（实测游标滞后常为 0–几 KB，
> 即已读到底），所以瓶颈不在本工具，而在 **WorkBuddy 何时把请求写进
> `~/.workbuddy/projects/**/*.jsonl`** —— 日志按消息粒度追加，一轮里连续跑多个
> 工具调用时，中间可能有一段时间没有新行可读，看板于是看起来"不动"。
> 判据就是上面那张卡的「监听」：`已读到底` 说明不是采集滞后。

## 诚实边界（务必向用户如实说明）

- **本工具无法拦截宿主自身的 LLM 调用**。它不改变模型计费，只能在**消费发生后极短时间
  （秒级）内**从日志读到并累计，据此发出告警、暂停标记、降级建议。
- 因此"不超预算"是**确定性规则 + 精确计量 + 快速反馈 + 人/agent 依约执行**的组合结果，
  而非内核级的硬截断。`enforce` 模式会把状态置为 paused 并让 `check` 返回 `STOP`，
  但是否真的停手取决于执行方（agent 或人）遵守协议。
- **「最佳完成度」不可保证**，只能定义并追求「**在预算约束下最大化预期质量**」：
  预算紧张时按优先级保住主干交付物。
- 金额是按**牌价**的粗略预估，依据 `core/pricing.py` 的 `PRICE` 表与峰谷规则；
  用户套餐不同应以实际账单为准。修改 `PRICE` / `PEAK_WINDOWS` / `HOL_RANGES` 即可适配。
- **牌价未知的模型，其金额是「假设值」而非实际计费**。`price_of()` 用最长前缀匹配
  `PRICE`，一个键都不命中就落到兜底档 `PRICE_DEF`。匿名/新上线模型很容易落进来
  （实测 `stealth/space-bunny-alpha` 即如此）。
  这类模型会在面板顶部显示 `⚠ N 个模型牌价未知`，`/api/state` 的 `pricing.unpriced`
  也会列出，**`used.cny` 只能当量级参考**。token 数是真实的（直接读日志），金额不是。
  补牌价：在 `PRICE` 里加一条前缀键即可，例如
  `"space-bunny": {"P": [入, 出, 缓存], "O": [入, 出, 缓存], "CW": 1}`。

## 实现要点（改代码前先读）

两条容易踩的实现约束，都是实测得出的：

1. **账本连接必须常驻、并由 `close()` 真正关闭**（`core/ledger.py`）。
   每次操作新开连接会让 WAL 反复建立/checkpoint/删除：实测本机 Windows
   单次操作 91–125 ms，账本初始化 1.3 s；改为常驻连接后降到 0.1 ms / 71 ms
   （约 15–20 倍）。账本在面板 SSE 与 watcher 的高频路径上，这个差距直接决定实时性。
   同时 `sqlite3.Connection` 会参与**引用环**，不 gc 就释放不掉 —— 不显式 `close()`
   会让 `reset` 的改名报 `WinError 32`。`Ledger.close()` 现在既 checkpoint 又真关连接，
   关闭后其他方法会自动重开，不会因关闭而不可用。
2. **`totals()` 必须带 `since` 口径**（`core/ledger.py`）。
   `plan` / `lean` / 按模型与按执行体分布都按 `meta.since_ts` 过滤，若 `totals()`
   不过滤，面板的"已用"就会把历史请求一直累加进来（曾出现"已用 4090%"）。
   `totals(task_id)`（终身视图，供 `task list` 用）保持不过滤。

## 四个实测踩过的坑（2026-09-28 已修，别再重复踩）

| 症状 | 根因 | 现在的行为 |
|---|---|---|
| 新任务一开工就显示「已用 ¥0.32 / 521 万 token」（全是历史） | `budget` 设置预算时**不动** `since_ts`，上一轮任务的统计起点被继承 | **设置预算 = 开启新账期**：`budget --tokens/--cny` 自动把起点推到此刻；只想改上限、不改起点请加 `--keep-since`；`--add-*` 追加预算不动起点 |
| `reset` 报 `WinError 32 ... ledger.db`（文件被占用） | 看守进程（respawn）持有账本句柄，且会立刻重拉面板 | `reset` 先停看守进程（pid 见 `<data-dir>/watch.pid`）再停面板；失败时的报错信息给出两条明确排障指令 |
| 面板显示「工作区 = 技能目录」→ **监听 0 个日志文件**、本会话消耗全部漏统计 | `respawn` 用 `cwd=HERE` 拉子进程，`--workspace auto` 于是被解析成技能目录 | `respawn` 在**调用者上下文**解析工作区（账本已记录则沿用记录，否则取当前目录），并把结果显式传给子进程；启动会打印 `[BOC] 监听工作区：…` |
| 金额才用 23%，`check` 却报 `STOP` | 两个上限（token / 金额）同时生效，拍脑袋设的 token 上限先触顶 | `check` 打印 `[口径提示]`：指明顶爆的是哪个口径、另一口径用了多少；只关心金额时，把 token 上限按同一口径设大（例：¥2 ≈ 1800 万 token 量级） |

> 用法提醒：**不要在技能目录里执行 `respawn`**。虽然现在会优先沿用账本记录的工作区，
> 但首次运行（账本里还没有记录）时仍取当前目录 —— 从技能目录执行就会统计到技能目录。
> 想指定工作区就显式传 `--workspace <slug>`（或 `--all`）。
